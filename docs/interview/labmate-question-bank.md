# LabMate 面试题库：高校共享仪器运维助手

本文围绕 LabMate 的业务设计、节点实现、检索取证、工具写入和评测展开。回答按当前代码与扩库后报告整理；先讲机制，再给实验室例子和已验证证据。

最新数字的类别分布、指标公式、失败、简历口径与 10 个评测追问见[完整评测报告](../14-evaluation-report.md)，全部题目、已有原答与业务变化见[逐题明细](../evaluation-casebook.md)；简明指标见[实测摘要](../../eval/LABMATE_MEASURED.md)，来源与 30 篇语料见[知识库说明](../labmate-corpus.md)。这些数据集由开发者 AI 辅助整理，只能作为回归结果。2026-10-31 的历史报告实际加载过 BGE small 与 bge-reranker-base，并包含 CPU 推理验证、固定权重与输入哈希；当前公开副本默认使用轻量回退，需按[模型运行文档](../20-model-runtime-and-eval.md)下载权重后再复测。10 月 30 日降级结果另存历史对照。

## 一、项目定位与模块设计

### 1. 用一分钟介绍项目

**答：** LabMate 是融合自适应检索与受控工具调用的高校共享仪器运维助手。它将实验室安全与预约知识检索、演示设备台账查询、时段检查，以及需要人工确认的预约和报修提案放在一条 LangGraph 工作流中。活动知识库有 30 篇 Markdown，其中 24 篇是 AI 辅助编写的项目演示规则；另有公开制度摘要和模拟台账。当前没有接入真实校园身份、预约平台或仪器控制器。

**展开与追问：** 把“知识、状态、动作”分别举例：培训要求来自文档；设备位置和状态来自工具；预约/报修来自确认后的本地写入。解释这三类请求为什么不能只用一次 top-k 检索，就能把项目动机和架构连起来。源码入口为 app/services/container.py 和 app/agents/graph.py。

### 2. 项目如何拆模块，模块之间怎样协作？

**答：** 按输入接入、图编排、证据检索、工具业务、会话持久化和评测拆分。API 只接收 ChatRequest 并返回 ChatResponse；ChatService 准备用户/会话状态、恢复确认提案，再调用 LangGraph。图节点依赖容器注入的模型、检索器和工具目录；工具通过仓储层访问当前请求的数据库会话。这样可以分别测试检索、路由、工具权限和数据库状态，而不必让每个测试都请求 DeepSeek。

例如设备查询落到 `app/tools/lab_tools.py` 和 `app/repositories/lab_repository.py`；普通制度问答进入 `app/retrieval/`。两条路径最终都把结构化结果交给生成节点，避免业务 SQL 或规则散落在提示词里。

**展开与追问：** 模块之间传 AgentState、RetrievedChunk、ToolResult 和 ChatResponse 等显式结构。数据库 session 用 ContextVar 绑定到请求，单例图不保存跨请求连接。可追问的取舍是当前节点仍直接依赖一些具体服务，后续可以引入更稳定的用例接口，但不能为了分层无限增加抽象。

### 3. 知识库里的 30 篇都是真实学校制度吗？

**答：** 不是。30 篇里只有部分是公开制度的摘要，摘要适用范围和核验状态记录在来源文档；24 篇是我按演示场景自拟并用 AI 辅助编写的规则；还有项目边界、模拟设备台账和案例。24 篇不会冒充学校校规或设备 SOP。

**展开与追问：** 检索元数据中的 source 主要是本地文件路径；真实来源链接和核验情况维护在资料说明与正文。没有实现自动逐条权威验证，也没有按学校/现行版本做完整过滤。因此命中片段后仍需检查适用范围，不可把多个学校条款拼成统一校规。

### 4. 为什么先用自拟规则扩充？

**答：** 目的是让工程能覆盖预约、交接、维护、样本和异常上报等检索路径，检查切块、路由和安全边界。它解决的是开发演示覆盖度，不是现实制度可信度。目标学校上线前必须替换或审核这些规则，并由管理员提供现行制度和型号手册。

**展开与追问：** 扩充时每个主题增加两条检索题，原有 27 条加 48 条形成 75 条。问题与文档由同一开发过程整理，有自我验证偏差；应补不看语料的独立提问、同义表达、不可回答问题和金标审核，不能仅靠增加文档数证明项目质量。

### 5. 这个项目算多 Agent 吗？

**答：** 不算多个自治 Agent。它是一张 LangGraph 状态图里的单 Agent、多节点工作流：护栏、意图、路由、规划、执行、生成和忠实度检查共享一份状态。工具按职责拆分，但没有多个 Agent 自主协商或独立对话。

**展开与追问：** graph.py 实际是护栏→指代补全→意图→路由→检索或 plan/execute→生成→忠实度→记忆。execute 后没有再回到 planner 的反馈边；Self-RAG 的迭代在检索内部。把有多个节点说成多自治 Agent，或者说模型会无限自行执行直到成功，都与当前图不符。

## 二、架构、RAG 与自我反思

### 6. 为什么不用一条固定 RAG 链？

**答：** 问候、安全拒答、制度问答、跨条件核对和台账操作的目标不同。系统将请求路由到 `DIRECT`、`REFUSE`、`SINGLE`、`MULTI` 或 `AGENT`：简单问候跳过检索，明确越界请求拒答，单条制度一次检索，多条件问题走迭代检索，设备/预约/报修走规划器和工具。

**展开与追问：** 路由解决成本、证据来源与风险差异，不保证天然节省费用。真实成本要统计分类、复杂度、改写、反思、生成和裁判等调用。当前报告没有固定 RAG 与自适应全流程的配对成本实验，所以面试可解释设计目的，不能编造节省比例。

### 7. `SINGLE` 和 `MULTI` 有什么区别？

**答：** `SINGLE` 做一轮取证：保留原查询与最多一个改写，混合检索、合并重排后生成并检查忠实度；`MULTI` 调用 Self-RAG 循环：查询改写、候选检索、重排、证据充分性判断，默认总计最多三轮。证据已充分就提前结束；证据不足时围绕缺失方面继续找。它是单工作流里的检索自检，不是第二个 Agent。

**展开与追问：** SINGLE 不是只查一个字符串：它会保留原查询及最多一个改写，各自取候选、按 chunk ID 去重后重排。默认每次检索 top_k=3，重排 top_n=5 为上限；MULTI 默认 top_k=8、最多三轮。离线检索消融采用自己的候选数，不能直接等同线上 SINGLE。

### 8. 项目中的 Self-RAG 如何实现？

**答：** `SelfRAGLoop` 每轮保留原查询并生成至多一个改写查询，合并去重候选后重排，再由模型以结构化 JSON 判断相关性和充分性。达到充分条件就停止；否则将缺失方面用于下一轮。模型或 JSON 失败时回退到是否有候选的简单判断，因此降级时反思质量会降低。

**展开与追问：** 每轮积累的片段按 ID 保留，停止条件实际看 sufficient，模型异常时 bool(chunks) 会把“有候选”当作“充分”。最终结果是积累顺序下截断到 rerank_top_n 的两倍，没有对全部历史片段重新全局排序。这些限制是下一步改进证据判断和多轮评测的重点。

### 9. 混合检索怎么组成？

**答：** Markdown 按标题切块，保留稳定 chunk ID、文档 ID 和章节。BM25 负责词项召回，向量检索负责稠密候选，RRF 按排名融合，之后由重排器选最终上下文。历史真实模型评测使用过 `BAAI/bge-small-zh-v1.5` 的 512 维向量和 `BAAI/bge-reranker-base` 重排；当前公开副本默认回退到哈希向量和词面重排。评测入口会先做真实推理检查，任一后端回退就停止。

**展开与追问：** Markdown 先按一至三级标题分段，长段再按 500 字符、60 字符重叠切窗；清洗后 SHA1 精确去重，SimHash 近重复只日志提示。document ID 基于相对知识路径，chunk ID 带序号，Qdrant point ID 从 chunk ID 派生。稳定性依赖文件名和切分不变，不是永远不变。

### 10. 这次评测证明向量融合提升了吗？

**答：** 在固定的 75 条开发题上，真实融合 P@1 73.3%，高于 BM25 的 68.0% 与单独 BGE 的 69.3%；Cross-Encoder 管线为 78.7%。这支持当前语料上的管线收益，不能泛化为所有问题。单独 BGE 的 R@3 82.7% 仍低于 BM25 87.0%，真实重排 R@3 89.7% 也低于历史词面路径 91.6%。

**展开与追问：** 评测里 BM25、单向量和普通融合各取五个候选；融合+重排先取八个再保留五个，所以重排对照也改变了候选范围。若要精确归因，需要固定候选池仅替换排序器。目前只能报告指定管线结果，不能把全部差值都归因于重排算法。

### 11. Self-RAG/自纠错带来多少提升？

**答：** 75/75 生成完成、失败 0，裁判不可用均为 0；无上下文忠实度 96.0%、不支持率 4.0%、关键词 49.33%，RAG 与自检均为 100% / 0% / 88.0%。本轮 RAG 首检全部通过，没有触发自纠错，不能声称证明自检收益；生成与裁判同为 DeepSeek，忠实度不等于人工正确率。

**展开与追问：** 生成评测只做一次混合检索，RAG+self_check 是答案生成后的支持性判断，不是完整 SelfRAGLoop。完整多轮收益还要同时比较答对率、支持证据、轮数、模型调用成本和延迟，尤其要有一次检索缺证据而补查成功的独立用例。

### 12. 引用如何保证？

**答：** 每个检索片段有 `chunk_id`、`document_id`、章节和来源元数据。生成输出允许返回引用 chunk ID，服务端只把这些 ID 映射到真实检索片段再返回给前端。引用能追溯证据片段，不自动证明答案完整或法律/校规解释正确。

**展开与追问：** 生成模型返回 citation_chunk_ids；generate_node 在实际检索候选和 search_knowledge 返回片段里查 ID，只映射存在的项目。引用必须进一步审查“是否支撑这句话”，不能由 ID 存在推断因果正确。修正答案后也要复核引用与新文本的一致性。

### 13. 知识库里的指令会影响 Agent 吗？

**答：** 检索内容按不可信上下文处理。系统提示规定只能依据证据回答，不能把文档里的文字当系统指令；工具目录由应用侧构建，危险操作还有服务端权限和确认检查。提示注入防护仍需持续测试，不能承诺绝对免疫。

**展开与追问：** 防护分三层：系统提示隔离不可信证据、规划目录限制工具名、执行层独立检查写风险。攻击文档即使影响模型输出，也不应突破这些服务端边界。但用户身份与知识版本治理仍有限，不能把 guardrail 正则或一次拒答当作完整安全证明。

## 三、意图、工具和安全边界

### 14. 意图识别是纯规则还是大模型？

**答：** 运行时优先用 DeepSeek 结构化分类，失败回退规则，可通过高精度覆盖层修正明显意图。固定 120 条开发样本上，规则 100/120（83.33%），DeepSeek 覆盖层开/关均 119/120（99.17%），异常和规则回退均为 0。

**展开与追问：** 覆盖层覆盖 87/120（72.5%），已覆盖准确率 87/87，分母不同。唯一误分为“夜间实验出现异常应该怎样上报”：lab_safety 被分成 lab_maintenance。提示根据首轮失败修正，非独立留出集；开/关同分，也未证明覆盖层额外收益。

**原题与证据：** [120 题、9 类说明](../../eval/dataset/labmate/README.md)列出数量和金标；[完整意图章节](../14-evaluation-report.md#7-意图识别分布对照逐类结果与失败)有四组字段、逐类正确数和原始 JSON。当前 rule_based_intent 内部已调用高精度短语规则，不能把它说成完全无覆盖逻辑的消融。9 类是本次题集分布，兼容枚举保留更多值。

### 15. 设备状态查询怎么避免编造？

**答：** 设备状态走 `get_lab_equipment_status`，读本地关系数据库中的设备记录，而不是让模型根据文本猜状态。未知设备会报未找到；答案应强调台账是模拟数据，不是 IoT 实时遥测。工具目录当前只有六项 LabMate 工具。

**展开与追问：** get_lab_equipment_status 返回 equipment_id/name/category/location/status/requires_training/notes，状态是台账值；requires_training 只是设备属性，当前没有训练资格表验证该用户已培训。未知编号报错后不能编造“可能在某房间”作为工具查询结果。

### 16. 为什么把设备、预约做成工具，不全放在 RAG 里？

**答：** 制度是非结构化文本，适合检索；设备状态、预约时段和报修单是结构化业务状态，需要 schema 校验和数据库查询/写入。检索只能解释规则，不能可靠地判断具体设备记录或创建可审计申请。

**展开与追问：** 结构化工具提供明确参数、业务校验和可断言数据库结果。RAG 回答“预约通常需要什么”，工具回答“本地记录中该时段有哪些申请”。两者放入同一答案时要把制度要求、当前台账事实和用户申请状态分开，避免混成已批准结论。

### 17. 预约确认前检查什么？

**答：** 需要设备编号、带时区的开始时间、结束时间和用途；结束晚于开始，开始在未来，演示系统限制最长八小时，并检查同设备与已有 requested/approved 时段是否冲突。写入状态是 `requested`，表示待审核，不代表管理员已批准。

**展开与追问：** 区间冲突条件为 existing.start_at < new.end_at 且 existing.end_at > new.start_at，首尾相接可以不冲突。时间转换 UTC 后入库；按日查询当前按 UTC 零点划分，并非 Asia/Shanghai 日界。查冲突后插入尚无数据库排他约束，不能承诺高并发下无双重预约。

### 18. 用户明确报修，模型规划错了怎么办？

**答：** 明确“帮我报修/登记报修”时，规划后会用确定性逻辑补齐报修工具步骤，并从原话提取设备编号。字段不足则追问；字段齐全先生成 `pending_action`。这条路径有针对性回归测试，不能直接执行写操作。

**展开与追问：** planner_node 会移除没有明确写意愿的写步骤，明确实验室写请求则补齐对应工具，再检查设备、时间、用途或故障等必填字段。这是确定性保护，而非模型自我反思自动修复。自然语言触发仍有限，含政策疑问词的混合请求需要更多回归题。

### 19. 人工确认具体保护什么？

**答：** 预约和报修属于写操作，先展示动作、参数与摘要，确认 ID 绑定到用户与会话并有过期时间。执行层再次检查工具风险；有幂等键时校验参数指纹、避免重复写入，并写审计日志。提案本身不等于工单；当前 E2E 另有确认后的数据库写入检查，写入也只代表演示系统已登记。

**展开与追问：** 未确认 pending_action 存在时 executor_node 直接跳过整个计划，因此提案轮不一定执行了前置读工具；实际设备和冲突要到确认后再次校验。确认请求由 ChatService 恢复保存的参数，router 强制 AGENT，planner 生成该动作的确定计划。提案本身不证明业务参数最终有效。

### 20. “没有冲突”为什么不等于可以上机？

**答：** 它只说明本地演示数据库没有记录到重叠时段。它不证明真实设备空闲、培训资格有效、样本通过审核或预约获批。演示台账、预约状态、操作资格和现场安全检查是不同事实。

**展开与追问：** 前后状态可以变化，确认前后的查询不是锁定设备。必须在写入时重新检查，未来接真实系统还要由权威预约服务负责原子占位和资格审批。助手目前只登记申请，不能把“无冲突”作为绕过管理员审核的理由。

### 21. 遇到设备报警或危险操作请求怎么回答？

**答：** 记录可观察现象，不推断具体原因；危险现场遵循所在实验室应急预案并联系管理员/安全员。没有具体型号手册时，不提供转速、压力、温度、复位或绕过联锁步骤。助手不控制真实仪器。

**展开与追问：** 报修支持记录现象、设备号和优先级，不提供故障根因诊断或手动拆修步骤。台账标记 maintenance 也不能说明实际仪器断电；系统没有执行器、PLC 或 IoT 接口。危险现场的行动应由本校应急预案和现场负责人决定。

### 22. 哪些知识问题系统当前答不了？

**答：** 对具体型号的厂家参数和 SOP、实时物联网状态、真实培训资格、真实预约审批、样本合规审批、费用结算或维修进度，当前没有权威数据接口。规则文件可以说明应向谁核实，但不等于系统实现了这些业务功能。

**展开与追问：** 知识文档提到的取消改期、计费核对、样本声明或数据导出，是演示规则和人工处理说明，没有相应业务表与工具闭环。面试展示接口目录即可说明“文本覆盖”和“可执行功能”的区别，后续扩功能需要补 schema、授权、仓储、确认与测试。

## 四、数据与业务可信度

### 23. 设备数据库是真实的吗？

**答：** 不是。设备编号、房间、状态、预约和工单都是项目模拟数据。开发和测试启动时只补充缺失的 LabMate demo 设备；它用于演示工具调用、冲突检查和确认流程，不连接学校平台或控制器。

**展开与追问：** container 仅在非 production 环境补缺失 demo 设备；不会每次把已有设备状态重置。可重复 seed 不等于真实数据同步。演示完整写流程时应使用隔离数据库，防止多次演示留下申请影响后续冲突判断。

### 24. 公开制度摘要和自拟规则如何区分？

**答：** 来源记录列出官方链接、正文保存状态和适用范围；原始 PDF 只有一份重庆大学文件。24 篇自拟规则带 `demo-ops-` 或 `demo-safety-` 前缀，并在文内声明是 AI 辅助编写的项目演示规则。不能把引用的多校链接说成已保存、逐条核验的原件。

**展开与追问：** 原件只有一份已保存的重庆大学 PDF；其他公开来源的正文与附件核验程度不同。RAG 正文是整理摘要，不是原件全文。自拟规则有固定 demo 前缀和版本，答复应保持“项目演示规则”范围，不把链接数量说成已收录的真实制度数量。

### 25. 能否用于真实高校生产？

**答：** 目前只能作为本地演示和工程原型。上线前需要目标学校审核知识和权限，接入可信身份、真实设备/预约平台、审计留存、管理员工作流和安全验证，并评估数据保护与部署运维。当前没有做这些生产集成。

**展开与追问：** 除了模型效果，还需可信身份、岗位授权、真实审批状态、多实例并发约束与生产恢复验证；本地会话属主校验和确认持久化已实现。当前测试多为受控单机路径，Postgres/Redis/Qdrant 的配置支持不能替代真实多实例验收。

## 五、指标、评测与方法限制

### 26. 当前有哪些指标确实重测了？

**答：** 真实模型完整复测包含 120 条意图开/关覆盖层、75 条四路检索、75 条生成自检，以及 32 个 E2E 场景（51 轮）。意图 119/120；生成 75/75 完成、失败与裁判不可用均 0；E2E 32/32 场景通过。后端 185、前端 3 项测试及前端构建通过。

**展开与追问：** 最新汇总为 all_20261031T140024Z.json；四份完整任务报告的输入、app/eval 源码、模型与包版本一致，source_reports 保留路径和 SHA256。首轮失败与额度中断记录保留；充值后才跑最终复测。问题虽然预先固定，开发期间根据失败修复过提示和逻辑，成绩属于开发回归，非独立泛化证明。

### 27. 最新检索指标怎么报告？

**答：** 固定 75 题上，BM25 P@1/R@3/MRR = 68.0%/87.0%/0.8056；真实 BGE 为 69.3%/82.7%/0.8082；RRF 为 73.3%/87.6%/0.8367；Cross-Encoder 管线为 78.7%/89.7%/0.8744。注明是开发小样本、指定文档金标，重排路径候选先 8 后 5。

**展开与追问：** P@1 是首个返回文档是否相关；R@3 是前三个去重文档覆盖的金标比例；MRR 看首个相关的倒数排名。指定目标文档不等于穷尽相关集合，汇总表的 min/max 是样本得分范围，不是置信区间，不能把它写成提升区间。

### 28. 最新生成指标是什么？

**答：** 75/75 生成完成、失败 0，裁判不可用均为 0；无上下文忠实度 96.0%、不支持率 4.0%、关键词 49.33%，RAG 与自检均为 100% / 0% / 88.0%。本轮 RAG 首检全部通过，没有触发自纠错，不能声称证明自检收益；生成与裁判同为 DeepSeek，忠实度不等于人工正确率。

**展开与追问：** FaithfulnessChecker 返回 supported、hallucinated_spans 和 rationale；checker_unavailable 与“模型确有事实幻觉”不是同一事件。报告保留 checker_failures，并将不可用计入不支持。拒答和表示不确定也可能被判忠实，所以还需要回答完整性和独立正确性评价。

**失败复盘：** [完整报告第 9 节](../14-evaluation-report.md#9-生成忠实度自检与关键词)逐题列出 9 条关键词未匹配，区分同义措辞与证据/信息遗漏。lr57 的保存答案还承诺提交费用异议，而当前没有此工具；同模型裁判仍通过，说明 100% 支持性不能替代能力边界和完整性审核。这是已发现、尚未声称修复的结果。

### 29. E2E 指标可以怎么说？

**答：** 32/32 场景通过，51/51 请求完成。有策略金标的请求 22/22、意图金标 26/26、关键词 22/22、拒答 3/3、提案 8/8；数据库无写入 16/16、工单变化 5/5、预约变化 9/9、回读与摘要恢复各 1/1。P50 3.86 秒、P95 14.03 秒。

**展开与追问：** 使用隔离文件 SQLite 真实确认并核对演示记录，覆盖冲突、重复确认、槽位补充和 4 次服务/图/引擎重建；模型 provider 复用。另有独立 Python 进程恢复测试。MULTI 四条均执行，一条实际 3 轮，其余 1 轮充分即停。关键词是词面指标；样本、网络与并行评测影响延迟，不能写成整体正确率或生产 SLA。

**分母追问：** le25 的“确认执行”实际标签是 out_of_scope，但服务端恢复确认提案后强制 AGENT 完成写入；该步仅配置完成/工单增量检查，没有意图金标。所以 32/32 场景不代表 51 次意图都正确。[51 次请求表](../evaluation-casebook.md#e2e-turns)保留真实标签、策略与每步断言，不把异常中间值改成理想路径。

### 30. 扩库前后分数能直接比吗？

**答：** 不能。文档从 6 篇变 30 篇，检索题从 27 条变 75 条，分布和干扰文档都变了。必须在相同数据集、相同知识库版本和相同后端上做配对实验，才可讨论改进。

**展开与追问：** 固定旧 27 题可以做知识扩充前后的配对回归，但当前总分同时换了语料规模和问题分布。报告完整 75 题之外，还要把稳定子集、每个主题和新增干扰分别分析，才能判断哪里真的改进或退化。

### 31. 评测集有什么偏差？

**答：** 语料、问题和目标文档金标都由开发者 AI 辅助整理，存在覆盖偏差和自我验证；目标文档不是穷尽相关性标注。同一个模型生成并裁判也会产生 judge bias。接下来要请独立标注者审核并补真实、去重、有来源的问题。

**展开与追问：** 独立评测不只是换一个 judge 名称，还需问题采集与金标制作独立。可让不了解语料编写过程的人提出问题，由两人审核相关文档和答案必要信息，分出不可回答集，并记录分歧。当前没有做这样的人工审核，不能说已有真实用户准确率。

### 32. 为什么之前 RRF 比 BM25 低，后来如何定位？

**答：** 公开副本的离线回退使用哈希向量；历史测量中曾出现单路 P@1 5.3%、哈希融合 45.3% 的诊断结果，噪声挤掉了 BM25 有效结果。核对 provider 后安装依赖、固定 BGE 权重并重新入库，在相同 75 题上历史真实 BGE 为 69.3%、融合为 73.3%。这说明应先核实后端和候选，再调融合参数；不能把占位路失败归咎于所有语义模型。

**展开与追问：** RRF 对不同分数尺度不敏感，对候选质量仍敏感。检查方法是保留两路原排名，找出 BM25 第一名被哪些哈希候选挤下；确认是不是噪声、重复或金标过窄，再决定是否门控第二路、调候选或更换模型。不能只因方法通用就假定融合有益。

## 六、工程实现与追问

### 33. 为什么选 LangGraph？

**答：** 请求需要条件分支和共享状态，图能显式表示护栏、意图、路由、检索或工具、生成和忠实度节点，便于看路径和分别测试。代价是状态契约与图编排复杂度；如果只有简单问答链，直接函数调用会更轻。

**展开与追问：** 图的优点是显式分支、状态契约和节点级测试；代价是跨节点字段约定、异常传播和资源生命周期复杂度。当前图编译一次，依赖通过 partial 注入，请求 session 通过 ContextVar 绑定；多轮步骤由有界循环处理，不需要为了展示 Agent 人为增加自治角色。

### 34. 当前数据库和基础设施配置是什么？

**答：** 本机运行使用 SQLite、内存缓存和内存向量库；可配置 PostgreSQL、Redis、Qdrant。健康接口显示就绪只代表已配置依赖按当前规则可用，不等于生产容量或高可用已验证。

**展开与追问：** health 不查库，ready 主要以数据库是否响应决定。capabilities 的 dense_backend 与 reranker 读取实际 provider；hybrid 只说明结构。当前应分别为 bge-small-zh-v1.5 和 cross-encoder。内存缓存/向量库仍会使 degraded 为 true，不等于模型失败；加载与输出质量还需真实推理和评测。

### 35. 是否有完整持久化、多实例确认？

**答：** 业务、消息、摘要、幂等及完整确认提案均存关系数据库。提案有 UTC 过期时间，15 分钟有效，恢复时校验用户、会话并使用服务端原参数；已验证服务重建与独立 Python 进程恢复。首次并发和多副本竞争仍不承诺 exactly-once。

**展开与追问：** pending_actions 与消息同事务提交，普通及 SSE 共用持久化路径。确认只提交 action ID，实际参数从数据库恢复，重复确认复用幂等结果。这不是 LangGraph checkpoint；过期提案自动清理、首次并发排他及真实多副本验证尚未完成。user_id 来自请求体，属主校验不能替代可信身份认证。

### 36. API 有哪些主要入口？

**答：** `GET /api/v1/health`、`GET /api/v1/ready`、`GET /api/v1/capabilities`、`POST /api/v1/chat`、`POST /api/v1/chat/stream`、管理员工具和技能目录，以及 `/metrics`。聊天响应含策略、意图、引用、待确认动作、错误和延迟信息。

**展开与追问：** SSE 的顺序为 started→node→token→answer→done，文本在最终校验后按 48 字符分段。用户可感知进度，但不是模型原始 token 即时转发。ChatRequest 带 stream 字段并不意味着普通 /chat 会变 SSE，流式应使用 /chat/stream。

### 37. MCP 远程工具接入了吗？

**答：** 容器在测试环境可以合并本地/配置的 MCP 工具适配，但当前非测试环境的 LabMate 工具目录是六个本地工具；没有宣称已有生产远程 MCP 服务或外部实验平台连接。

**展开与追问：** Skill 是 JSON 描述和工具白名单，通过触发短语优先、意图映射其次选一个；MCP 是工具调用适配层，两者职责不同。当前非测试容器没有合并远程 MCP 业务，不能因为 adapter 和测试存在就说已对接学校服务。

### 38. 记忆和上下文压缩怎么做？

**答：** 已恢复数据库摘要和最近 20 条消息；护栏后补全明确指代，路由、检索与规划使用 resolved_query，生成提示注入有限历史和摘要。达到 12 条消息后合并旧摘要更新。基础跨轮、槽位补充和摘要恢复已接通；完整提示预算和长期记忆仍未完成。

**展开与追问：** 生成背景限制为最多 8 条近期消息、单条 600 字符、摘要 1600 字符、合计最多 6800 字符；历史不能当实时事实或写入授权。三级阈值 50%/70%/85%、工具预览 400/160 字符、窗口四轮仍保留，压缩在回答之后，因此不是完整回答前预算。

### 39. 如何验证写操作可靠性？

**答：** 除 schema、权限、确认绑定和参数指纹单测外，真实 E2E 在隔离文件数据库中核对提案前不写入、确认后工单/预约数量、冲突和重复确认。集成测试额外覆盖过期、跨用户、两个独立进程先提案后确认，以及 SSE answer 事件前提案已入库。

**展开与追问：** 执行层优先用 confirmed_action_id 作为幂等键，对工具和排序参数 JSON 做 SHA256。同键同参复用结果，同键异参冲突；正常请求最终 commit。预约冲突先查后写，首次并发竞争尚未排他，顺序幂等不等于并发 exactly-once。

### 40. 下阶段最优先做什么？

**答：** 优先补独立审核的问题与金标，固定候选池分析重排，测 MULTI 的实际收益、成本和失败用例。基础持久确认与记忆恢复已完成，接下来完善校园时区、数据库并发约束、提案清理、长对话预算，再接可信身份及真实业务平台。

**展开与追问：** 按独立题集与失败样本→固定候选池/MULTI 配对→时区与首次并发→可信校园接口推进。已验证的恢复是本地服务重建和独立进程退出恢复，不扩展为生产灾备承诺；每次变更知识、金标或算法保存版本与配置。

## 简历表述

> 面向高校共享仪器运维构建融合知识检索与工具执行的智能助手，构建包含公开制度摘要与 AI 辅助编写演示规则的 30 篇知识库；实现自适应路由、Self-RAG 迭代检索、设备查询、预约冲突检查及带用户确认的报修/预约提案。扩库后在 75 条开发回归题上测得 BM25 P@1 68.0%、R@3 87.0%，并完成 75 条 DeepSeek 生成评测和 32 个 E2E 场景（51 轮）测试；设备及流程数据为本地模拟数据。2026-10-31 历史真实模型测量中的 BGE 融合与 Cross-Encoder 管线 P@1 为 73.3% / 78.7%；公开副本默认不携带模型权重，未接入真实校园平台。

面试时需要补充的评测条件：问答集由开发者 AI 辅助整理；同模型裁判可能偏乐观；检索分数不代表生产泛化。
