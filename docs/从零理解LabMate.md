# 从零理解 LabMate：高校共享仪器运维助手

> 这是一份给第一次接触 RAG、Agent 和后端项目的读者写的说明。你不需要先会编程。建议先读前半部分理解“它解决什么问题、一次请求会经过什么步骤”，再把后半部分当作术语词典和代码地图。
>
> 本文描述的是当前仓库里的 LabMate 实现。活动知识库有 30 篇 Markdown、108 个文本片段，其中 24 篇是 AI 辅助编写的自拟演示规则；设备、预约和工单也是本地模拟数据。因此它适合学习和演示系统设计，回答不能当成任何真实学校的正式制度或实时设备信息。

## 1. 先用一句话认识项目

LabMate 是一个高校共享仪器运维助手：用户可以问实验室规则，可以查询演示台账里的设备和预约情况，也可以申请预约或登记报修；涉及写入数据的动作，要先展示申请内容并由用户确认。

可以把它想成实验室前台的数字助手。它做三类事情：

| 用户需要什么 | 助手去哪里找 | 例子 |
|---|---|---|
| 规则知识 | 实验室资料库 | “仪器使用前要检查什么？” |
| 当前业务状态 | 本地演示数据库 | “LAB-CF-01 在哪里？” |
| 修改业务记录 | 受控工具和数据库 | “帮我登记这台设备的故障” |

这三类信息不能混为一谈。资料库适合回答“规则是什么”；数据库适合回答“演示记录现在是什么”；写入工具负责“把用户确认的申请登记进去”。聊天模型自己并不知道某台真实仪器的实时状态，也不会真的维修仪器。

## 2. 先区分普通聊天模型和 RAG

### 普通聊天模型像一位闭卷答题者

语言模型（LLM，Large Language Model）读过大量文字，可以理解问题并组织语言。但它回答时主要依靠训练中学到的内容和当前对话，可能不知道你项目里的资料，也可能把不确定的内容说得很肯定。

想象你问一位没拿到实验室手册的临时接待员：“这台设备能连续预约几个小时？”他可能按常识猜一个答案。流畅不代表答案有依据。

### RAG 像先翻手册，再根据手册回答

RAG 是 Retrieval-Augmented Generation 的缩写，中文常说“检索增强生成”。名字分成两部分：

- **检索（Retrieval）**：先从资料里找出与问题相关的段落。
- **生成（Generation）**：再让语言模型根据这些段落整理答案。

例如，用户问预约时长，LabMate 先从资料库找出预约规则片段，再把问题和片段交给模型，最后回答并提供来源引用。可以把流程记成：

```text
用户的问题 → 找相关资料 → 根据资料组织答案 → 展示答案和引用
```

检索到资料不代表答案一定正确；有引用也不代表引用内容完整或权威。知识库本身的来源和质量仍然很重要。

### RAG 解决了什么，又没有解决什么

RAG 让回答能使用项目自己的资料，并能指出依据来自哪里。更新知识时，也可以更新资料库，而不必重新训练语言模型。

RAG 不会自动保证资料真实、最新或没有矛盾，也不会自然获得数据库里的实时信息。LabMate 把资料检索和业务数据库查询分开，正是因为它们回答的是不同类型的问题。

## 3. 什么是 Agent？为什么它不是“多 Agent 项目”？

### Agent 的白话理解

Agent（智能体）可以理解为“会根据目标判断下一步、必要时使用工具的程序”。普通问答通常是“收到问题 → 生成文字”；Agent 工作流还可以是“理解目标 → 选择工具 → 执行查询或动作 → 根据结果继续回答”。

例如：“看看 LAB-CF-01 有没有空，再帮我申请明天下午两点到三点，用途是课程实验。”系统需要理解用户意图、查询业务数据、整理申请字段，并在写入前等待确认。这类任务只靠从文章里找一段文字不够。

### Agentic RAG 是什么

Agentic RAG 通常指带有规划、路由、工具使用或迭代检索能力的 RAG 系统。LabMate 具备这些元素：它会分类问题、选处理策略；复杂知识问题可以多轮查证；需要查设备或处理申请时可以规划并调用工具。

“Agentic”描述的是系统处理问题的方式，不表示里面一定有很多个 Agent。

### 单 Agent、多节点，与多 Agent 的差别

LabMate 用一张 LangGraph 状态图编排多个步骤。分类、路由、检索、规划、工具执行、生成和检查是图里的不同节点，它们共享同一份请求状态。可以把它比作一个人按流程经过多个岗位，而不是多个独立员工互相讨论。

因此，准确的说法是：**这是一个带有 Agent 工作流的 RAG / Agentic RAG 项目；当前实现是单 Agent、多节点，不是多 Agent 协作系统。** 多 Agent 通常意味着多个相对独立的 Agent 有各自角色或上下文，并需要互相委派、沟通或协调；仅仅有多个函数、节点或工具，并不等于多 Agent。

## 4. 一条问题从进入系统到得到答案，会发生什么？

下面以“离心机使用前要做哪些安全检查？”为例。主流程大致是：

```text
用户问题
  ↓
输入安全检查
  ↓
补全必要的对话背景
  ↓
判断用户想做什么
  ↓
判断问题复杂度并选择路径
  ↓
查资料或调用工具
  ↓
生成答案
  ↓
检查答案是否有证据支持
  ↓
保存本轮对话和必要摘要
```

每一步的作用如下：

1. **输入安全检查（guardrail）**：检查输入是否越界或要求绕过安全规则。越界请求可以直接拒绝。
2. **对话背景补全**：如果用户说“它在哪里”，系统尝试根据最近对话理解“它”指什么。它保留原问题，也单独记录补全后的问题，避免覆盖用户原话。
3. **意图分类（intent classification）**：判断用户在问规则、查设备、申请预约、报修、安全问题还是闲聊。
4. **复杂度路由（routing）**：根据问题决定直接回答、检索一次、多轮检索、调用工具或拒绝。
5. **检索或工具**：查制度问题时找知识片段；问设备状态时读本地演示数据库；申请预约或报修时先准备待确认提案。
6. **生成（generation）**：模型根据证据、工具返回结果和有限对话背景组织自然语言。
7. **忠实度检查（faithfulness check）**：检查答案中的说法是否得到提供给模型的证据支持；必要时尝试修正或退回较保守的答案。
8. **记忆更新**：保存用户和助手消息；较长对话会生成摘要，供后续轮次理解背景。

不是每个问题都会走过所有步骤。问候通常直接回答；规则问题会检索资料；设备查询会用工具；越界请求会拒绝。

## 5. 五种处理策略：系统如何决定走哪条路

LabMate 使用五个策略。它们是**同一个系统的路线选择**，不是五个 Agent：

| 策略 | 通俗说法 | LabMate 中的用途 |
|---|---|---|
| `DIRECT`（直接） | 不查资料，直接处理 | 问候、简短对话或总结用户刚提供的信息 |
| `SINGLE`（单轮检索） | 查一次相关资料再答 | 查一条比较明确的制度或常见问题 |
| `MULTI`（多轮检索） | 查完先判断够不够，不够再补查 | 问题包含多个条件、需要组合证据时 |
| `AGENT`（工具工作流） | 规划并调用业务工具 | 查询设备、检查时段、准备预约或报修申请 |
| `REFUSE`（拒绝） | 不处理这个请求 | 超出助手范围或要求绕过安全规则 |

这个判断叫**自适应路由**：系统尝试根据问题选择合适成本和能力的路线。路由本身也可能判断错，所以项目需要意图评测、端到端场景测试和失败案例分析。

## 6. 检索是怎么找到资料的？

### 第一步：把长文切成小块

文档如果很长，检索时直接把整篇都拿出来不够精确，也会占用模型上下文。因此入库时会做**切块（chunking）**：把文档拆成较小片段，并保留文档标题、章节和片段编号。

当前实现先按 Markdown 标题分节，再用大约 500 个字符的窗口切分，相邻窗口重叠大约 60 个字符。重叠像撕纸时留一点搭边，可以减少一句话刚好被切在两块边界时丢失上下文的情况。

每个片段有稳定的 `chunk_id`。稳定编号让引用能指向具体资料片段，也便于重复构建索引时定位同一块内容。

### 第二步：用两种方法找候选片段

#### BM25：看问题和资料是否用了相同的词

BM25 是一种经典的关键词检索算法。可以把它理解成更聪明的“全文搜索”：如果用户问“离心机使用前检查”，包含“离心机”“检查”等词的片段通常会排得更靠前。它适合设备编号、专有名词和明确词汇。

它的弱点是同义表达：用户写“开机前确认”，资料写“启动前检查”，字面词不同，BM25 可能不容易把两者对应起来。

#### Embedding / 向量检索：比较意思是否接近

Embedding（嵌入）模型把一段文字转换成一串数字，这串数字叫**向量（vector）**。意思相近的文字，经过模型编码后通常在向量空间里也更接近。

例如，“仪器启动前的检查”和“开机之前需要确认的事项”用词不同，但向量检索有机会识别它们语义相似。历史真实模型评测中，LabMate 加载过 `BAAI/bge-small-zh-v1.5`，输出 512 维向量；当前公开副本默认使用哈希向量回退，下载权重并打开配置后才会加载 BGE。

向量不是一句可读的摘要，也不是数据库里存的自然语言答案；它是用于计算相似度的数字表示。Embedding 模型也不是生成答案的 DeepSeek，它负责把文字转换成向量。

### 第三步：把关键词和语义结果合起来

BM25 的分数和向量相似度分数尺度不同，直接把两个原始分数相加可能不公平。LabMate 使用 RRF（Reciprocal Rank Fusion，倒数排名融合）：它看某个片段在不同检索结果里的名次，再把名次合并。

公式是：

```text
RRF 分数(片段) = 对每一路检索结果求和：1 / (k + 该片段在此路的名次)
```

源码默认 `k=60`。名次越靠前，得到的贡献越大；一个片段如果在多路结果中都排得靠前，融合后更可能留下。RRF 合并的是排名证据，不是 BM25 和向量的原始分数。

### 第四步：用 Cross-Encoder 再排序

粗检索适合快速从大量片段里找候选；候选中仍可能有不够相关的内容。**重排（reranking）**会再比较“用户问题 + 候选片段”的相关性，把更匹配的片段往前放。

历史真实模型评测中，LabMate 加载过 `BAAI/bge-reranker-base` Cross-Encoder。Cross-Encoder（交叉编码器）把问题和候选文字放在一起计算匹配程度，通常比单独向量相似度更细，但逐个处理候选会增加计算成本，所以一般先召回一批，再重排较小的候选集。当前公开副本默认使用词面重排，具体运行状态以 `/api/v1/capabilities` 为准。

可以把整条检索链记成：

```text
BM25 找“词相同”的候选
    + 向量检索找“意思相近”的候选
    → RRF 合并候选排名
    → Cross-Encoder 细排
    → 把最相关的片段交给生成模型
```

### 第五步：用引用告诉读者依据在哪里

答案的引用指向检索到的文档或片段。引用有助于复核，但它本身不证明答案完全正确：模型可能引用了相关段落却漏掉关键条件，也可能把片段理解错。因此项目还做答案支持性检查，且知识资料的来源仍需人工审核。

## 7. Self-RAG：为什么有时要“查了再想想还缺什么”

普通单轮 RAG 通常是“检索一次，然后生成”。如果问题有多个条件，一次检索可能只找到其中一部分。LabMate 的 `MULTI` 路线实现了 Self-RAG 风格的循环：

```text
改写或补充查询
  → 检索并重排
  → 判断现有证据是否相关、是否足够
  → 足够：停止
  → 不足：围绕缺失方面继续查（最多三轮）
```

例如，用户同时问“设备异常后先做什么、需要通知谁、什么情况下必须停止使用”，系统可能需要分别找到操作、安全和上报规则，再判断证据是否覆盖问题的几个方面。

这里的 Self-RAG 是**检索过程中的证据充分性反思**。当前实现使用结构化模型输出判断，并非训练论文中特殊反思 token 的实现。模型判断“足够”也不是数学证明；如果判断调用失败，当前代码会按是否有候选作较简单的回退。

要把两种“检查”分开记：

| 检查 | 发生时机 | 要回答的问题 |
|---|---|---|
| Self-RAG 证据充分性检查 | 生成答案之前，每轮检索之后 | “目前找的资料够回答所有方面了吗？” |
| 答案忠实度检查 | 生成答案之后 | “答案里的说法有没有得到现有证据支持？” |

一次完整的 `MULTI` 运行说明循环确实执行过，但不自动证明它比单轮检索效果更好。证明“效果更好”还需要在合适的固定题集上做对照实验。

## 8. 工具调用：读数据和改数据不是一回事

### 工具是什么

工具（tool）是模型或工作流可以调用的、边界明确的程序接口。它不是模型凭空“真的会做事”，而是程序允许它调用一段具体代码，并由代码去查询或写入数据。

当前活动业务目录里的六个工具是：

| 工具名 | 做什么 | 风险类型 |
|---|---|---|
| `search_knowledge` | 搜索实验室知识资料 | 只读 |
| `search_lab_equipment` | 按名称、类别或位置查演示设备台账 | 只读 |
| `get_lab_equipment_status` | 按设备编号读取演示状态和位置 | 只读 |
| `check_lab_equipment_availability` | 查询演示预约占用时段 | 只读 |
| `request_lab_equipment_reservation` | 登记预约申请 | 写入 |
| `create_lab_maintenance_ticket` | 登记报修工单 | 写入 |

查询类工具读取数据；预约和报修会修改数据库记录，所以它们的风险更高。系统不能把“用户问规则”误当成“用户授权写入”。

### 预约/报修的完整确认过程

以“帮我给 LAB-CF-01 登记报修，它持续振动”为例：

1. 系统识别这是报修意图，并提取设备编号和故障描述。
2. 如果必要字段缺失，就先追问；不会用“待用户提供”这种占位文本伪装成完整申请。
3. 字段齐全后，系统生成一张待确认提案，展示将要登记的工具和参数。
4. 此时还没有执行写入。用户确认后，服务端根据提案 ID 取回当时保存的原始参数。
5. 执行前再次核对设备和业务条件，再把工单写进本地演示数据库。
6. 最后回复“演示工单已登记”。这不表示维修已经完成、设备已经停机或厂家已收到通知。

预约也遵循类似流程。预约申请状态不等于管理员批准，不等于用户已经取得设备操作资格。

### HITL、事务、幂等分别是什么意思

- **HITL（Human-in-the-Loop，人类在回路中）**：重要动作由人参与确认。LabMate 对写操作先展示提案，再等待用户确认。
- **事务（transaction）**：数据库把一组相关变更作为一个整体提交，避免只保存了半套状态。项目会把关键写入和幂等记录放在请求事务中。
- **幂等（idempotency）**：网络重试或用户重复点确认时，同一个已处理动作尽量复用结果，避免再登记一条重复记录。
- **提案过期**：待确认提案保存 15 分钟；确认时从服务端恢复参数，不信任客户端重新提交一套参数。

当前已有顺序重复确认保护，并测过提案恢复；但尚未实现首次并发确认排他，也没有证明高并发下严格的 exactly-once（恰好执行一次）保证。`user_id` 目前也不是由可信校园身份认证系统绑定的。演示系统因此不能被描述成生产级审批或权限平台。

## 9. 对话记忆是什么？能不能把它当数据库事实？

多轮对话中，用户可能先说“样品编号是 X17”，下一轮再问“它在哪里”。系统需要保存一部分历史，才能理解“它”或“刚才那份样品”指什么。

LabMate 会加载最近最多 20 条消息和会话摘要。明确的简单指代可以补全；含糊的指代不应该随便猜设备编号。历史用于理解上下文，不取代实时设备查询，也不能代替预约/报修的明确确认。

长对话会生成摘要以减少重复携带全部历史的负担。摘要是模型压缩后的文字，可能漏掉细节，所以它不是精确、无限的长期记忆。当前实现有界地注入历史，并在较长对话中更新摘要；完整精确 token 预算和长期记忆机制仍有限。

简单区分：

- “我刚才说的样品编号是什么？”可以根据对话记忆回答。
- “设备现在是否空闲？”应该查业务数据，不能根据旧对话猜。
- “请现在替我提交报修。”仍要经过字段核验和确认，历史中提过故障不代表本轮已有授权。

## 10. 项目中的 API、数据库、前端和流式返回

- **前端（frontend）**：用户看到并操作的网页界面。仓库里有 React 前端。
- **后端（backend）**：接收请求、运行工作流、查询模型和数据库的服务。项目使用 Python/FastAPI。
- **API（Application Programming Interface）**：前端和后端约定的通信入口。聊天接口例如 `POST /chat`；路径表示“向服务发送一条聊天请求”。
- **数据库（database）**：按结构保存会话、消息、设备、预约、工单和待确认动作的地方。当前演示业务数据保存在本地数据库。
- **JSON**：一种常见的数据交换格式，用字段组织信息，例如 `{"equipment_id":"LAB-CF-01"}`。
- **SSE（Server-Sent Events）**：服务器向网页持续发送事件的一种方式。LabMate 的流式接口会先发送进度事件；最终答案经过检查并保存后再发送，避免把未验证的模型草稿直接展示为最终结果。
- **Trace ID（追踪编号）**：给一次请求分配的编号，方便把日志和阶段耗时对应起来。

这些工程组件让一个 RAG 想法变成可以运行、调试和演示的应用，但它们本身不等于 RAG 算法。

## 11. 项目指标应该怎么读

指标是“在什么题目、用什么方法、按什么规则得到的数字”。看数字时要同时看分母、题集来源和测量限制。

### 意图识别：系统有没有认出问题类型

当前固定开发题集有 120 条意图题。DeepSeek 结果为 119/120，即 99.17%；规则基线为 100/120，即 83.33%。这里的“准确率”就是预测正确数除以题目总数。

这 120 条题目用于开发和回归，失败案例曾被用来改进提示和路由，所以这不是独立留出集上的泛化成绩，也不应直接理解成面对真实学生时必然达到 99.17%。

### 检索指标：正确资料排得靠不靠前

75 道检索题的主要结果：

| 路线 | Precision@1 | Recall@3 | MRR |
|---|---:|---:|---:|
| BM25 | 68.00% | 87.00% | 0.8056 |
| BGE 向量检索 | 69.33% | 82.67% | 0.8082 |
| BM25 + BGE + RRF | 73.33% | 87.56% | 0.8367 |
| 融合 + Cross-Encoder 重排 | 78.67% | 89.67% | 0.8744 |

- **Precision@1 / P@1（排名第一的精确率）**：第一条结果是否命中标注目标。
- **Recall@3 / R@3（前三条的召回率）**：标注相关资料是否在前三条中找到。它关注“有没有找到”，不强求排第一。
- **MRR（Mean Reciprocal Rank，平均倒数排名）**：正确结果越靠前，单题贡献越大；最后对题目取平均。

融合加重排这条路线在检索题上取得最高的这些数值，但它先取 8 个融合候选，再重排留下 5 个；其他路线候选设置不同。因此整体变化不能全部归功于 Cross-Encoder 单一因素。题集也是开发回归题集，标注可能没有覆盖所有相关文档。

### 生成指标：答案是否有依据

75 道生成题全部完成。裁判给出的 RAG 忠实度为 100%，关键词命中为 88%（66/75）。无上下文回答的忠实度为 96%，关键词命中为 49.33%。

需要特别小心解释：首轮 RAG 答案已经全部通过，本轮没有触发自我纠错，因此“RAG + 自检”与 RAG 的结果相同。它不能证明自检带来了额外提升。忠实度裁判由同一个 DeepSeek 模型执行，衡量的是它认为答案是否受证据支持，不等同于专家人工确认的事实正确率。

### E2E 和自动化测试：业务流程有没有走完整

E2E（End-to-End，端到端）测试从完整请求开始，检查系统响应和数据库变化。当前报告里 32/32 个场景通过，共完成 51/51 次请求，覆盖预约/报修提案、确认写入、重复确认、冲突和恢复等。

此外，报告记录后端 185 项测试通过，前端 3 项测试通过且构建通过。自动化测试有助于发现代码回归，但不能替代真实生产用户、真实校园身份和真实设备系统的验证。

### 延迟：一次请求用了多久

本轮 51 次 E2E 请求的 P50 为 3.86 秒、P95 为 14.03 秒。P50 表示一半请求不超过约 3.86 秒；P95 表示约 95% 的请求不超过约 14.03 秒（按该报告使用的分位数算法）。这包括远程模型 API 和 CPU 本地推理。

这些时间来自小规模开发运行，不能当成生产 SLA（服务等级承诺），也不能说明所有网络、并发和时段下都一样快。

完整方法、条件、失败记录和限制见[当前实测报告](../eval/LABMATE_MEASURED.md)。

## 12. 容易混淆的专有名词白话词典

| 名词 | 白话解释 | 在本项目里的对应 |
|---|---|---|
| LLM | 能理解并生成文字的语言模型 | DeepSeek 用于意图、路由、生成等模型任务 |
| RAG | 先检索资料，再根据资料生成答案 | 查知识库片段后回答并附引用 |
| Agent | 能判断步骤并使用工具完成任务的程序 | 规划器和工具节点组成的单 Agent 工作流 |
| Multi-Agent | 多个相对独立的 Agent 分工并协调 | 当前项目不属于这种架构 |
| Agentic RAG | 把路由、工具或迭代检索等 Agent 能力用于 RAG | LabMate 的整体技术类型之一 |
| Workflow / 工作流 | 按条件连接起来的一组步骤 | LangGraph 里的节点和分支 |
| Node / 节点 | 工作流中的一个处理步骤 | 意图分类、检索、生成、执行工具等 |
| State / 状态 | 节点之间传递的请求信息 | 当前问题、检索片段、工具结果、最终答案等 |
| Intent / 意图 | 用户这句话想完成的事情类别 | 安全咨询、设备查询、预约、报修等 |
| Routing / 路由 | 根据问题选择系统接下来走哪条路线 | 选 `DIRECT`、`SINGLE`、`MULTI`、`AGENT` 或 `REFUSE` |
| Corpus / 语料库 | 供检索的整套文档 | 当前 30 篇 Markdown 活动资料 |
| Ingestion / 入库 | 清洗文档、切块并建立检索所需数据 | 构建 BM25 和向量索引 |
| Chunk / 片段 | 从长文切出的一小段文字 | 最多约 500 字符、相邻段约重叠 60 字符 |
| Embedding / 嵌入 | 把文本编码成数字向量 | BGE small 中文模型生成 512 维向量 |
| Vector / 向量 | 一串用于计算相似度的数字 | 表示问题或片段的语义特征 |
| BM25 | 根据词语匹配程度排序的检索算法 | 关键词检索通道 |
| Dense Retrieval / 稠密检索 | 用向量寻找语义相近内容 | BGE 向量检索通道 |
| Hybrid Retrieval / 混合检索 | 结合多种检索方法 | BM25 + 向量检索 |
| RRF | 根据多个排序列表的名次进行融合 | 合并关键词和向量候选排名 |
| Reranker / 重排器 | 对初步候选做更细的相关性排序 | Cross-Encoder BGE reranker |
| Cross-Encoder | 把问题和候选文本一起计算匹配程度的模型 | 用于精排检索候选 |
| Self-RAG | 检索中检查证据是否足够，必要时继续查 | `MULTI` 路线，最多三轮 |
| Faithfulness / 忠实度 | 答案说法是否能从提供的证据得到支持 | 生成后的检查；不等于事实真值保证 |
| Citation / 引用 | 指向支持答案的文档或片段 | 返回真实检索到的 chunk 引用 |
| Tool / 工具 | 工作流能调用的一段明确程序能力 | 查询台账、查询时段、登记申请等 |
| Planner / 规划器 | 把用户目标整理成工具步骤 | `AGENT` 路线中的任务规划组件 |
| Executor / 执行器 | 按计划调用工具并收集结果 | 检查风险后运行读或写工具 |
| HITL | 需要人确认的重要动作流程 | 预约和报修写入前的用户确认 |
| Pending action / 待确认提案 | 暂存、等待用户确认的动作和参数 | 最长 15 分钟，从服务端恢复原参数 |
| Idempotency / 幂等 | 重试时避免重复造成相同副作用 | 重复确认尽量复用已登记结果 |
| Transaction / 事务 | 把相关数据库变更作为一组提交 | 保障关键写入的一致性 |
| SQLite | 轻量级关系型数据库 | 测试和本地演示可用的数据库之一 |
| SQLAlchemy | Python 中操作 SQL 数据库的工具库 | 项目用它访问关系数据库 |
| FastAPI | Python 的 Web API 框架 | 提供聊天等后端接口 |
| SSE | 服务器持续向网页推送事件的机制 | `/chat/stream` 的进度和答案事件 |
| JSON | 用字段表达数据的文本格式 | API、模型结构化结果和工具参数常用格式 |
| Token | 模型处理文字时使用的切分单位 | 提示长度、输出长度和 API 用量单位 |
| Trace ID | 一次请求的追踪编号 | 把同一次请求的日志和计时关联起来 |
| E2E | 从完整入口到最终结果的端到端测试 | 检查真实工作流和数据库变化 |
| Baseline / 基线 | 用于比较的简单或已有方案 | 规则意图分类、BM25 等对照方法 |
| Ablation / 消融实验 | 拿掉一个部件，比较结果变化的实验 | 用来验证某个组件是否真的贡献效果 |
| P50 / P95 | 延迟分布中的中位附近值和高分位值 | 描述请求耗时，不代表固定上限承诺 |

## 14. 一个适合初学者的完整口头讲解

可以这样介绍项目：

> 我做了一个高校共享仪器运维助手。规则问答使用 RAG：先对实验室资料做切块，通过 BM25 关键词检索和 BGE 向量检索找候选，再用 RRF 融合，并由 Cross-Encoder 重排，最后让大模型根据证据生成带来源的答案。系统会根据问题选择直接回答、单轮或多轮检索、工具工作流或拒绝。需要查设备和预约状态时调用本地模拟数据工具；预约和报修属于写操作，会先保存待确认提案，用户确认后再校验并写入。系统是一张 LangGraph 状态图中的单 Agent、多节点工作流，不是多 Agent 协作。项目也测了意图、检索、生成、端到端流程和自动化测试；当前成绩属于开发回归，演示语料和业务数据不是生产校园数据。

讲解时有三个重要边界要说清楚：

1. **实际接了什么数据**：资料库包含自拟演示规则，设备与业务台账是模拟数据。
2. **结果能说明什么**：报告说明固定开发题集上的表现，不能直接当作生产环境泛化保证。
3. **还没实现或证明什么**：没有真实校园身份和设备平台接入；没有完整证明多轮自检收益，也没有严格 exactly-once 并发保证。

## 15. 零基础自测：能不能用自己的话答出来？

先尝试不用看答案解释下面问题；答不出来时回到对应章节：

1. 为什么用户问“设备目前在哪”时，不能只查知识文档？
2. RAG 中“检索”和“生成”分别做什么？
3. BM25 和向量检索各自擅长什么？为什么把它们合起来？
4. RRF 为什么看排名，而不直接把两路分数相加？
5. Cross-Encoder 的排序发生在检索流程的哪个位置？
6. `SINGLE` 和 `MULTI` 有什么区别？证据充分性检查与答案忠实度检查分别发生在哪里？
7. 为什么有很多节点和工具，也不代表这是多 Agent 项目？
8. 预约提案出现后，数据库是不是已经写入？用户确认后服务端从哪里恢复参数？
9. “幂等”能解决什么问题？它是否等于任何并发场景下保证恰好执行一次？
10. 为什么 99.17% 的意图准确率不能直接当作真实用户准确率承诺？

如果能说明“信息从哪里来、系统为何选这条路线、动作是否写数据库、指标的分母和限制是什么”，就已经抓住了项目最核心的逻辑。

## 16. 当前实现与限制，一页记住

| 已实现并有相应验证 | 当前边界 |
|---|---|
| BM25、真实 BGE embedding、RRF、真实 Cross-Encoder 检索链路 | 评测是 75 条开发题集，金标可能不穷尽相关文档 |
| `DIRECT`、`SINGLE`、`MULTI`、`AGENT`、`REFUSE` 策略路由 | 意图题集参与过开发修正，不是独立留出验证 |
| Self-RAG 风格最多三轮的证据补充循环 | 本轮生成首检全部通过，未证明自检带来额外收益 |
| 六个活动工具、预约/报修待确认提案和数据库写入 | 设备与台账是模拟数据，没有真实仪器控制 |
| 提案持久化、服务重建后的恢复、顺序重复确认保护 | 未证明首次并发确认排他或 exactly-once |
| 最近消息、摘要和有限的指代补全 | 摘要可能丢细节，不是无限长期记忆或精确 token 预算 |
| 后端、前端及 E2E 自动化测试 | 小规模测试不构成生产 SLA、安全认证或校园身份认证 |

写简历或面试回答时，使用“实现了什么、在哪些题目和条件下测过、还没有证明什么”这三层表达，会比只报一个高准确率更可靠。
