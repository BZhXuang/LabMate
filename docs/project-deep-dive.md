# LabMate 项目深入讲解

LabMate 将高校共享仪器运维中的三类问题放进一套工作流：制度需要文本证据，设备与时段需要数据库事实，预约/报修需要校验和人工确认。理解项目时沿一次请求看数据如何变化，比仅记框架名更有用。

## 1. 需求如何分成知识、状态和动作

“使用前要完成哪些培训”由制度知识回答；“LAB-CF-01 在哪里、台账是什么状态”由设备工具回答；“帮我登记报修”会产生业务记录。文档内容无法替代实时台账，模型不能只根据聊天意愿直接写库。系统因此分别提供检索分支和工具分支，再在生成层整合证据。

当前活动知识库为 30 篇 Markdown，其中 24 篇是自拟演示规则。设备位置、状态、预约和工单是本地模拟数据；规则覆盖了更多人工流程，但可执行工具只有六个。培训审批、取消预约、费用结算和设备控制没有实现业务闭环。

## 2. 启动时构建哪些对象

`build_infrastructure()` 创建异步数据库 engine/session factory 与可选 Redis；`build_retrieval()` 选择 embedding、解析与切块、建立 BM25/向量索引并创建重排器；`build_container()` 选择 DeepSeek 或离线回答、注册六个工具、创建 ChatService 并编译 LangGraph。

图和工具目录按进程复用，AsyncSession 每次请求单独绑定到 ContextVar，避免把某个请求的连接放进单例对象。开发/测试启动补缺失 demo 设备；production 不自动 seed。模型开关、模型实际加载与业务数据存在是三个独立条件。

## 3. 请求接入与状态契约

ChatRequest 包含 message、user_id、session_id、confirm_action_id 和 idempotency_key。ChatService 限流、选择会话、校验确认、读取最近最多 20 条消息，然后初始化 AgentState。

| 状态组 | 字段示例 | 谁负责 |
|---|---|---|
| 标识 | trace_id、user_id、session_id | 请求接入与 ChatService |
| 决策 | intent、complexity、strategy | 意图和路由节点 |
| 证据 | retrieved_chunks、tool_results | 检索/执行节点 |
| 动作 | plan、pending_action、confirmed_action | 规划器与确认恢复 |
| 展示 | final_answer、citations、refused | 生成与忠实度节点 |
| 统计 | latency、token_usage、extra | 节点与服务汇总 |

节点返回局部字段更新，不用无限追加消息 reducer。当前已检查已有会话的 user_id 属主，拒绝跨用户读取；但 user_id 仍由请求方填写，尚未绑定可信身份认证，不能把字符串 ID 当成真实身份。

## 4. 图如何路由

输入护栏先拒绝明显注入、越界与危险设备控制请求。剩余请求先经过 resolve_context 补全明确指代，保留原问并生成 resolved_query，再经意图和复杂度分类后走 DIRECT、SINGLE、MULTI、AGENT 或 REFUSE。分类优先结构化模型结果，失败回退规则；设备编号等明确工具模式还会进行确定性纠偏。

图的 AGENT 分支是 plan→execute→generate，执行后不返回规划器；它是有界计划，不是无穷自主循环。多次取证发生在 SelfRAGLoop 内。整个项目是一张共享状态图中的单 Agent 多节点流程。

## 5. 一次制度问答的检索链

入库按标题分块，长段使用 500 字符窗口、60 字符重叠；清洗后精确去重，得到本次的 108 个片段。document ID 基于相对知识根路径，chunk ID 带序号，源路径与章节用于引用。

SINGLE 对原查询和最多一个改写分别检索：BM25 与向量路各取候选，RRF 按 ID 合并排名，再统一重排。默认单次 top_k=3、rerank_top_n=5 为上限；候选少时不会补满。BM25/向量在当前方法内顺序调用，不是已经并行执行。

检索缓存只保存知识候选，键为 query+top_k，默认 60 秒，没有语料版本。更新知识后要清缓存或等 TTL。设备工具不通过该缓存读取业务状态。

## 6. MULTI 的反思循环

SelfRAGLoop 每轮基于 missing_aspect 改写，保留原问题、检索去重、重排并积累候选，再判断证据是否充分。充分提前退出，默认最多三轮。模型或 JSON 失败时按有无候选回退，可能过早停止。

最终积累按保留顺序截断，并未对所有历史片段再次全局精排。生成后忠实度检查是另一阶段：判断具体答案是否被证据支持，失败时修正或保守回退。当前 75 条生成评测只用一次混合检索，未证明完整 MULTI 的额外价值。

## 7. 预约与报修工具的参数与状态

| 工具目标 | 必填字段 | 主要校验 | 成功结果 |
|---|---|---|---|
| 设备状态 | equipment_id | 编号格式、记录存在 | 台账字段，不是遥测 |
| 某日时段 | equipment_id、date | 设备存在，按 UTC 日期查询 | requested/approved 时段 |
| 预约申请 | equipment_id、start_at、end_at、purpose | 带时区、未来、正时长≤8 小时、available、无重叠 | requested 申请 |
| 故障登记 | equipment_id、issue | 设备存在、故障长度、priority 枚举 | open 工单与审计 |

冲突使用区间交集：existing.start < new.end 且 existing.end > new.start。首尾相接不冲突；requested 和 approved 都阻塞时段。当前按日查询使用 UTC 零点，尚未按校园本地时区划分日期；查后写也没有数据库级排他约束，不能保证高并发无重复预约。

## 8. 写操作的两次请求

首次用户明确提出动作，规划器抽取字段并补齐明确的写工具；缺字段追问，齐全生成 ActionProposal。当前 executor 看到未确认提案会跳过整个计划，因此提案轮不保证前置读工具已执行，业务参数最终可执行性要在确认时验证。

提案在 pending_actions 数据库表保存完整服务端参数和 UTC 过期时间，有效期 15 分钟，绑定用户和会话；与当轮消息一起提交。确认请求携同 session_id/user_id/action_id，服务端验证后恢复已存参数；路由强制 AGENT，规划器使用确定动作，避免模型重新理解“确认”而修改目标。前端收到提案不等于申请已写入。

## 9. 幂等、审计与事务边界

执行器优先使用确认 action ID 作为键，工具名与按键排序的参数 JSON 做 SHA256 指纹。同键同参复用先前结果，同键不同参冲突。仓储写业务行和审计，ChatService 保存对话后 commit。

这处理顺序重试，不是并发 exactly-once 证明。两个首次请求可能同时查询不到幂等记录，预约也可能同时通过冲突检查；需要数据库约束与失败恢复测试。某些工具异常被捕获成 ToolResult 后请求仍可能提交，不能笼统承诺任一步出错都会回滚全部图步骤。

## 10. 生成、引用与流式展示

答案模型收到当前问题、补全问题、有限历史与摘要、意图、策略、最多六个知识片段和工具结果；返回结构化 answer 与 citation_chunk_ids。服务端只映射实际片段/知识工具返回中的引用，捏造 ID 不会成为真实来源。

pending_action 和缺字段提示可以提前确定性返回。SSE 在图运行时发 node 进度，最终经检查后将答案按 48 字符分段发 token，再发 answer/done；不是原始模型 token 直接透传。离线或解析失败可给证据节选，但不能将节选当成完成的推理答案。

## 11. 会话和压缩实际做到哪里

消息和摘要持久化，初始化恢复 summary 与最近 20 条消息。resolve_context 保留原问并补全明确指代；生成提示注入最多 8 条近期消息及摘要，背景只用于理解，不充当事实和授权。压缩节点仍在当前回答之后。默认 128k 预算采用字符启发式，50%/70%/85% 对应工具预览、窗口和摘要，判级未覆盖全部提示内容。

本轮补齐摘要恢复、历史注入和基础指代/槽位验证；达到 12 条消息时合并旧摘要更新。确认也已入库，独立进程可恢复提案。完整提示的回答前 token 预算、长期记忆和多副本竞争仍待完善，详见[业务闭环与恢复](21-workflow-memory-and-recovery.md)。

## 12. 如何用证据讲结果

扩库后 120 条意图、75 条检索/生成和 32 个 E2E 场景（51 轮）已完成；历史测量时后端 185 项测试通过。2026-10-31 的历史模型运行实际加载了 BGE small 与 bge-reranker-base，BM25 P@1 68.0%，BGE 69.3%，RRF 73.3%，Cross-Encoder 管线 78.7%；重排管线也与普通召回用了不同候选数，不能把全部差异归因于算法。当前公开副本默认使用离线 provider、哈希向量和词面重排；重新启用本地模型后才能复现模型路径。

75/75 生成完成、失败 0，裁判不可用均为 0；无上下文忠实度 96.0%、不支持率 4.0%、关键词 49.33%，RAG 与自检均为 100% / 0% / 88.0%。本轮 RAG 首检全部通过，没有触发自纠错，不能声称证明自检收益；生成与裁判同为 DeepSeek，忠实度不等于人工正确率。
